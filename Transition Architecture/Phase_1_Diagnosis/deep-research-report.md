## Best-practice findings that matter most for GeoSee

### One transition clock should own visible progress

Browser animation best practice is clear: `requestAnimationFrame()` is a repaint-aligned, one-shot callback whose progress should be computed from the supplied frame timestamp, otherwise animation speed will drift on high-refresh-rate displays. MDN also notes that the callback timestamp is shared across same-origin windows and iframes, which is a useful architectural signal: if GeoSee wants camera, overlays, labels, legends, section frames, and entity opacity to feel like one transition, they should all resolve from a **single transition clock** rather than mixed timers or subsystem-local elapsed-time counters. citeturn21view0turn21view1

That aligns directly with the prompt’s own invariant that overlays and camera should live on the transition clock rather than separate timing paths. In practice, the combination of the prompt and browser guidance points toward a simple runtime test: every visible transition family should be provable as a function of one timestamped progress scalar, and interruption/replan should update that ownership explicitly rather than allowing multiple concurrent clocks. fileciteturn0file0L86-L90 citeturn21view0turn21view2

### Composition rules should be explicit per channel

The Web Animations specification offers a strong analogy for transition-runtime design. It defines an **effect stack** per property and says final values are produced by combining effect values in composite order. It also formalizes composite operations such as `replace`, `add`, and `accumulate`, and distinguishes **discrete** properties from genuinely interpolable ones. Discrete properties are specifically described as not additive, with a step-like swap rather than continuous interpolation. citeturn6view5turn6view6turn22view1turn22view2

That maps cleanly onto the GeoSee prompt. The prompt’s “surviving frames interpolate, changed/added/removed dissolve” rule is, in effect, a composition policy. Its note that discrete color/material channels matter is another composition rule. The practical implication is that GeoSee’s transition runtime should continue to treat different channels differently: transforms, extents, and some opacity paths can interpolate; identity, incompatible materials, helper basis changes, and other discrete channels should be routed through replace-or-dissolve semantics rather than forced through a universal tween path. fileciteturn0file0L83-L90 citeturn6view5turn6view6turn22view0turn22view2

### Interruption and replan should be modeled as explicit lifecycle states

W3C’s SCXML recommendation describes an event-based state-machine model built from states, transitions, `onentry`, `onexit`, and explicit transition selection semantics; it also supports parallel states when multiple regions must advance together. For a transition runtime, that is a strong best-practice argument for putting interruption, deferred flushes, settle, commit ownership, and replan under one explicit lifecycle model instead of letting those responsibilities leak across unrelated scene and UI subsystems. citeturn17view0

This matters because several of the prompt’s listed invariants are lifecycle invariants rather than geometry invariants: single commit owner, deferred-flush suppression, readiness/attach behavior, interruption/replan correctness, and no commit-time replay pop. Those are exactly the areas where an explicit state machine tends to outperform ad hoc booleans and handoffs. That does **not** automatically mean a rewrite is needed; it means the current runtime should be evaluated against explicit ownership and transition-state semantics when Phase 1 reproductions are gathered. fileciteturn0file0L86-L90 fileciteturn0file0L116-L130 citeturn17view0

### Helper objects should be stable and updated, not rebuilt opportunistically

The prompt’s helper-related invariants point to stability: no per-tick helper rebuild, right-handed helper basis, and numeric verification such as determinant and world bounding box checks. three.js’s own `PlaneHelper` documentation reinforces that shape of solution: it updates itself through `updateMatrixWorld()` based on its current plane and size, and it exposes `dispose()` for GPU-related cleanup. In other words, helper objects are expected to be **long-lived runtime objects with controlled updates and explicit lifecycle cleanup**, not constantly recreated throwaways. fileciteturn0file0L83-L90 fileciteturn0file0L100-L108 citeturn9view3

## The regression-test net should be the main durable deliverable

The attached brief is explicit that the regression-test net should be treated as the durable mechanism that prevents future breakage. External testing guidance strongly supports that stance. Playwright recommends testing **user-visible behavior**, isolating tests from each other, and avoiding dependency on third-party systems outside the tester’s control. Its fixtures are explicitly isolated between tests, which is the right property for reproducing transition families without state leakage. fileciteturn0file0L147-L149 citeturn14view0turn15view0

For time-dependent runtime behavior, Playwright’s clock support is especially relevant. It can override `Date`, timeouts, intervals, `requestAnimationFrame`, `performance`, and related browser timing APIs, and it supports fixed time, fast-forwarding, pause points, and manual ticking. That makes it unusually well suited for deterministic browser-side transition tests where the same scene needs to be asserted at specific time slices. citeturn12view0turn13view2

For observability, Playwright recommends traces on CI retries instead of relying only on screenshots or videos, and its trace tooling can record screenshots and DOM snapshots for later inspection. It also supports `toHaveScreenshot()` assertions for image-based regression checks. That combination is a good fit for Phase 1 evidence gathering because it supports both human review and automated guardrails. citeturn12view1turn13view3turn13view4turn6view7turn13view1

For pure plan-only tests outside the browser, Node’s built-in test runner is also a strong fit. It supports subtests, stable mock timers, and controllable mocked `Date` behavior, which is useful for transition-plan execution, interruption semantics, and composition logic that should not require a browser to validate. The Node docs are explicit that mock timers are a technique for making time-dependent tests more reliable and predictable, and that mocked time can be advanced deterministically. citeturn6view9turn16view0turn16view1turn16view2turn16view4

A practical GeoSee net therefore looks like this, as a synthesized recommendation rather than a claim about current repo coverage: browser tests for visible interpolation, legend behavior, screenshots, and traces; Node tests for plan generation, composition policy, commit/settle, and interruption semantics; and a small deck-state matrix per behavior family, carefully labeled as deck-state evidence only. The prompt’s own family list provides the starting taxonomy for that suite: section move/dissolve, MT scalar-family behavior, volume/threshold/slices, seismic families, overlays, legends/labels, camera, fog/background, commit/settle, readiness/attach, and interruption/replan. fileciteturn0file0L116-L130 citeturn14view0turn15view0turn12view0turn12view1turn16view0

## Best current harden-vs-rewrite call

The best current call is **incremental hardening first, rewrite only on evidence**. That is an inference, not a final Phase 1 verdict, because the prompt itself requires live reproductions before a definitive recommendation can be made. Even so, the prompt’s framing strongly favors this default: it says recent targeted fixes already landed, asks those fixes to be verified before being re-litigated, and says architecture work before residual-defect knowledge is backwards. fileciteturn0file0L26-L31 fileciteturn0file0L96-L108

The practical reason this inference makes sense is that the requirements already look like a runtime that **can** be hardened if three things become explicit and well-tested: one transition clock, explicit per-channel composition policy, and explicit lifecycle ownership for interruption/commit/settle. None of those imply a mandatory greenfield engine by themselves. They imply the need for disciplined verification and a much stronger synthetic-family test net. citeturn21view0turn6view5turn6view6turn17view0turn12view0turn15view0

The threshold for switching from incremental hardening to re-architecture should therefore be evidence-based. A rewrite becomes justified only if Phase 1 shows that the same failure primitive crosses multiple behavior families, or that the current runtime cannot express expected behavior as a deterministic plan driven by a single clock with explicit composition and lifecycle ownership. Until that happens, the cheapest decision-useful path is to verify the landed fixes, publish the open defect families with hard evidence, publish the clean list, and wire those families into deterministic regression coverage. That is the exact convergence logic the prompt is asking for. fileciteturn0file0L137-L149 citeturn6view5turn17view0turn14view0turn12view0
